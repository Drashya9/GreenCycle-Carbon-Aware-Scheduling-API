# 🌿 GreenCycle — Carbon-Aware Scheduling API

Run your dishwasher when the grid is greenest.

GreenCycle fetches a 24-hour carbon-intensity forecast, runs an O(n) sliding-window
algorithm over it to find the cleanest contiguous block of hours, and either hands you
the answer directly or schedules it and fires a webhook when the window starts.

Originally a Spring Boot service; rewritten in Go to lean into what Go is actually good
at: real concurrency, a long-running background scheduler, and a small, explicit
dependency set.

---

## What's here

| Area | How |
|---|---|
| **Concurrency** | `/calculate` races every configured grid provider concurrently (`context` + `select`, first success wins); `/calculate/multi` fans out across zip codes through a bounded worker pool |
| **Real scheduler** | A background goroutine loop claims due runs atomically (`UPDATE ... WHERE status='pending'`), fires a webhook + writes a notification, and catches up anything that should have fired while the process was down |
| **Caching + rate limiting** | Forecasts are cached in Redis (TTL); outbound calls to each real grid provider are throttled with a token bucket |
| **Postgres + real migrations** | Versioned SQL migrations (`golang-migrate`, embedded in the binary), not ORM-autogenerated schema |
| **Docker Compose** | App + Postgres + Redis + Adminer, one command |
| **Dashboard UI** | A vanilla HTML/CSS/JS frontend, embedded into the Go binary via `go:embed` — no separate frontend service, no build step, one deployable artifact |

## Running it

### Option A — Docker Compose (recommended)

```bash
cp .env.example .env    # defaults work out of the box with GRID_PROVIDERS=mock
docker compose up --build
```

This starts Postgres, Redis, Adminer (a DB browser at http://localhost:8081), and the
app on **http://localhost:8080** — which is also where the dashboard UI lives. Open it
in a browser to calculate optimal windows, compare zip codes, manage appliances, and
create/cancel scheduled runs, all against the live API. Migrations run automatically on
startup.

### Option B — Locally

Requires Go 1.26+, a running Postgres, and (optionally) a running Redis:

```bash
go run ./cmd/server
```

Set `DATABASE_URL` / `REDIS_URL` env vars (or a `.env` file) to point at your instances.
If Redis isn't reachable, the app logs a warning and runs uncached rather than failing.

### Running tests

```bash
go build ./... && go vet ./... && go test ./...
```

## Dashboard UI

A plain HTML/CSS/JS frontend at **http://localhost:8080/** (or wherever `PORT` points),
served by `internal/httpapi/server.go` directly out of the `web/` directory — embedded
into the compiled binary via `go:embed`, so there's nothing extra to build, deploy, or
run. It's the same origin as the API, so it just calls the endpoints below with `fetch`.

Four tabs, each exercising a real piece of the backend:

| Tab | Backed by |
|---|---|
| **Calculate** | `GET /calculate` — pick an appliance and zip, see the optimal window |
| **Multi-Zone** | `GET /calculate/multi` — compare several zip codes at once, greenest one highlighted |
| **Appliances** | `GET/POST/DELETE /appliances` — full CRUD |
| **Schedules** | `POST /schedules`, `GET /schedules`, `DELETE /schedules/{id}` — create, watch status flip from `pending` as the scheduler engine fires runs (auto-refreshes every 15s), cancel |

The status pill in the top bar polls `/health` every 10s.

## Endpoints

### `GET /calculate?appliance=Dryer&zip=85281`

Races every configured grid provider, caches the winner's forecast in Redis, and runs
the sliding-window algorithm.

```json
{
  "startTime": "2026-08-27T04:00:00Z",
  "endTime": "2026-08-27T05:00:00Z",
  "averageCarbonIntensity": 119.9,
  "applianceName": "Dryer",
  "recommendation": "Run your Dryer at 4:00 AM UTC — avg. 120 gCO₂/kWh (done by 5:00 AM UTC).",
  "provider": "mock"
}
```

### `GET /calculate/multi?appliance=Dryer&zips=85281,90001,10001`

Fetches every zip code concurrently (bounded worker pool, default 5 — `MULTIZONE_WORKERS`),
racing all configured providers for each one.

```json
{
  "applianceName": "Dryer",
  "results": [
    { "zip": "85281", "window": { "...": "..." } },
    { "zip": "90001", "window": { "...": "..." } }
  ],
  "greenest": { "...": "the lowest-averageCarbonIntensity window across all zips" }
}
```

### Appliances

- `GET /appliances` — list
- `POST /appliances` — `{"name": "Hot Tub", "durationHours": 3.0}` → 201
- `DELETE /appliances/{id}` → 204, or 404 if it doesn't exist

Seeded on first startup: Dishwasher (1.5h), Washing Machine (1h), Dryer (1h),
EV Charger (8h), Pool Pump (4h), Water Heater (2h).

### Scheduling

- **`POST /schedules`** — `{"applianceName": "Washing Machine", "zip": "85281", "webhookUrl": "https://webhook.site/..."}`
  Computes the optimal window (same pipeline as `/calculate`) and persists it as a
  pending run. `webhookUrl` is optional — omit it to use `SCHEDULER_WEBHOOK_URL`.
- `GET /schedules?status=pending` — list, optionally filtered
- `GET /schedules/{id}` — check status: `pending` → `fired` (or `failed`, with `lastError` set)
- `DELETE /schedules/{id}` — cancel while still pending → 204, or 404 once it's no longer pending

The background engine polls for due runs every `SCHEDULER_POLL_INTERVAL` (default 15s),
claims each one atomically so concurrent ticks can never double-fire, and — on startup —
immediately fires anything that should have run while the process was down (flagged
`firedLate` in the webhook payload). Every fire writes a `notifications` row regardless
of whether the webhook itself succeeded.

### `GET /health`

Reports Postgres and Redis connectivity:

```json
{ "status": "UP", "service": "GreenCycle", "checks": { "database": "up", "redis": "up" } }
```

## Configuration

All configuration is environment variables — see [.env.example](.env.example) for the
full list with defaults. The important ones:

| Variable | Default | Notes |
|---|---|---|
| `GRID_PROVIDERS` | `mock` | Comma list, e.g. `mock,electricitymaps,watttime` — raced concurrently per request |
| `ELECTRICITYMAPS_API_KEY` | — | Enables the `electricitymaps` provider when set ([get a key](https://www.electricitymaps.com/)) |
| `WATTTIME_USERNAME` / `WATTTIME_PASSWORD` | — | Enables the `watttime` provider when both are set ([register](https://www.watttime.org/)) |
| `FORECAST_CACHE_TTL` | `15m` | Redis cache TTL per (provider, zip) forecast |
| `GRID_RATE_LIMIT_RPS` | `2` | Outbound request cap per real provider |
| `SCHEDULER_WEBHOOK_URL` | — | Default webhook target; a schedule can override it per-request |

**Never commit real API keys or `.env`** — it's gitignored. If you're testing the
scheduler locally, [webhook.site](https://webhook.site) gives you a free URL to watch
payloads land in real time.

## How the algorithm works

Same O(n) sliding-window approach as the original:

```
Forecast (24 hours):  [180, 160, 145, 135, 130, 140, 180, 220, ...]
Appliance duration:   3 hours → window size = 3 slots

Iteration 1:  sum([180, 160, 145]) = 485   ← new minimum
Iteration 2:  sum([160, 145, 135]) = 440   ← new minimum (slide right)
...
Winner: index 3, starting at Hour 4
```

Each slot is visited exactly twice (once entering the window, once leaving) — O(n) time,
O(1) space.

## Design notes

- **Provider racing** (`internal/grid/race.go`): each provider gets its own goroutine; a
  `context.WithTimeout` + `select` on a shared channel takes the first success and cancels
  the rest, so slower in-flight HTTP calls are abandoned rather than wasted.
- **Scheduler correctness** (`internal/scheduler/engine.go`): the claim is a single
  `UPDATE scheduled_run SET status='fired' ... WHERE status='pending' RETURNING *` —
  that compare-and-swap is what prevents two overlapping poll ticks (or two instances)
  from firing the same run twice, with no application-level locking needed.
- **Cache before rate limit**: providers are wrapped `Cached(RateLimited(base))`, so a
  cache hit costs nothing against the rate limiter — only real outbound calls are
  throttled.
- **Real migrations, not AutoMigrate**: schema changes are versioned SQL files embedded
  into the binary, so the Docker image needs nothing but the compiled executable.
